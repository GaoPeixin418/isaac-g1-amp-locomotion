## ⚠️ 3.2 结论更正（2026-10-27）——上一节的"完全消除"是**假的**

> **更正原则**：原文保留不删。错误结论及其修正过程本身就是本项目最有价值的
> 记录之一（用户要求保留错误结论的更正记录）。

### 用户用眼睛推翻了我的结论

用户 10-27 看完 ft_walk10 / walk10_follow 反馈：

- "都还是有跛行存在，而且还蛮明显的"
- "左腿/左脚着地之后明显往上勾起来了，然后再慢慢下落下去，右腿/右脚明显更自然"
- "比 lam050_multi10_12 里走得好的机器人还差"

而模型数据在 3.1 节说 AI = 0.3%（人类水平）。**指标与观测矛盾时，先查口径**
（项目铁律 3：免责声明救不了口径错误）。

### 错误根因：`analyze_limp.py` 的接触阈值以单点最小值为基准

```python
# v1 的错误写法
thr = float(z.min() + 0.3 * (np.median(z) - z.min()))
on  = z < thr
```

`z.min()` 是**单个采样点**。只要某只脚出现过一次离群的低点（穿透/数值抖动），
阈值就被钉到异常低处，后续几乎只有那一个瞬间算"着地" —— duty 被系统性压低，
而两只脚的离群程度不同，于是 AI 完全失真。

同一份 `gait_model_6400.npz`，换不同口径的结果：

| 口径 | model_6400 @1.0 duty AI | 结论 |
|---|---|---|
| v1（`z.min()` 基准） | **0.3%** | "跛行消除"（错的） |
| v2（百分位 p5+12%·IQR，稳健） | **19.0%** | 仍有明显不对称 |
| 真实接触力 `foot_force_z` | duty AI 1.6%，峰力 AI 3.3% | 承重**时长/力度**确实对称了 |

**三个口径给出三个答案 → 说明 duty 这个量本身就不适合用来判断用户看到的现象。**

### 更深的问题：指标选错了对象（这才是核心教训）

用户主诉是"**这条腿在硬撑 / 脚勾起来慢慢放**"，是**出力不对称 + 足端轨迹形态**。
而我一直在测"脚接触地面多久"（duty / stance / 接触力）—— 这是两个不同的物理量。
它们的因果关系很弱：一只脚出力大一倍，完全可以做到接触时长一样长。

> 翻译成铁律：主诉现象 → 行为特征 → 标量。第二步必须忠于第一步的**物理量**，
> 不能挑一个"顺手能算的替代品"。duty 是替代品，不是特征。

### 重新量化：改用左右腿同名关节扭矩 RMS（直接测"出力"）

`scripts/analyze_leg_effort.py`，29 DOF 排布 **[0:6]=一条腿，[6:12]=另一条腿同名关节**。

### ⚠️ 第 4 次指标陷阱：单阈值接触判定把步频系统性高估

第一次测参考动作步频得到 **197.9 steps/min**，比人类步行 (100–115) 高出近一倍。
这是算法噪声不是真实步频：`z <= thr` 这种单阈值判定，足端高度贴着阈值时
会来回跳，每个小抖动都被算成一次"着地"。

修法（`gait_metrics2.contact_hyst`）：

1. **迟滞（Schmitt trigger）**：低于 `lo` 才算接触，要高于 `hi` 才算离地，`hi > lo`；
2. **最小接触/腾空时长**：短于 0.12 s 的段直接合并掉；
3. **自相关交叉验证**：用髋 pitch 主周期反推步频。原理完全不同，
   两个算法给出同一个数才可信（模型 2400：接触计数 150.0，自相关 150.0 ✅）。

修完参考步频从 197.9 降到 95–103，与人类文献吻合。

> 补记：v1 还犯过第四个错——按速度**掩码取帧**会把连续步态切成碎片，
> 边界处信号跳变，自相关主峰乱掉（参考侧 acad=283 vs 接触计数 131）。
> 所以参考侧改成**整段 clip 测量**再按均速插值。

2. **但对称性在回升变差**：legAI 42.6%→48.7%。
   说明扭矩对称惩罚（权重 -1.0）在后期**压不住**任务奖励把策略推向
   "步幅更大 + 单腿省劲"的方向。

### 根因（机制推断）：对称惩罚的 EMA 窗口被"加快左右交替"绕开

惩罚项是 `rel = |m_L − m_R| / (m_L + m_R + 1)`，其中 `m = EMA(τ²)`，
时间窗 `time_constant = 0.4 s ≈ 半个步态周期`。

关键在：EMA 是低通滤波。步频越高，0.4 s 窗口里左右交替次数越多，
**瞬时**的 m_L 和 m_R 就被平均得越接近 —— 即便每一步单腿的做功并不对称，
"瞬时出力比"也会被刷小。这等于给策略留了一个"加快步频来降低惩罚"的漏洞，
和"碎步"现象自洽。

**注意：这是机制推断 + 相关性，不是受控消融的硬结论。**

### 下一轮的修复方向（按治本程度排序）

1. **把"瞬时出力比"换成"每步做功比"（治本）**：
   `W = EMA(|τ·ω|)`（时间窗 ≥ 2 个步态周期），`asym = |W_L − W_R|/(W_L + W_R)`。
   做功是路程累积量，加快频率不能把它平均掉 → 从根上消除 exploit。
2. **低成本近似**：把现有 `time_constant` 从 0.4 拉到 1.5 s（≥2 个步态周期），
   让 EMA 覆盖完整周期，左右腿各自的周期均值才能如实进入惩罚。
3. **压制回升**：对称惩罚权重 -1.0 → -2.0，抵消后期任务奖励的优势。
   （但要配合 1 或 2，否则只是把"碎步"逼得更严重。）

> 铁律：iter 400 那个 26.1% 看着漂亮，但速度只有 0.06 m/s —— **站着不动
> 当然左右对称**。所以监控表强制带速度列，v_act < 0.4·v_cmd 的行直接标无效。

## 3.4 v2 根治方案（2026-10-27 21:31 从零训，seed 42）

### 三个病是一条因果链，不是一个病

v1 只治了对称性，结果对称性刷低了、代价是碎步 + 蹲姿。复盘后确认因果链：

```
蹲（膝一直弯、躯干压低）
   └─> 腿的有效摆长变短 ─> 步长只有参考的 65%（0.89 vs 1.22 m）
         └─> 为满足 1.0 m/s 只能提高步频 ─> 136–150 vs 参考 95–103
               └─> "像快走" / 转弯时支撑面切换过频 ─> 看着不稳
```

**而 v1 的对称惩罚自己留了后门**，把这条链越拧越紧：

- `W = EMA(τ²)`，时间窗 0.4 s ≈ **半个**步态周期（参考周期约 1.2 s）。
  步频越高，窗口内左右交替次数越多，τ² 被平均得越接近 1
  → **加快步频就能刷低不对称** → 蹲 + 碎步被同时奖励。
- τ² 还有第二个漏洞：等长收缩（关节几乎不动、纯撑着）时 ω≈0，
  真实做功为 0，但 τ² 很大 → 把"站着撑"误判成"在使劲"。

### v2 的四项改动（`scripts/patch_sym_v2.py`）

| 项 | 改法 | 治什么 |
|---|---|---|
| `leg_torque_asymmetry` → **`leg_work_asymmetry`** | 量 τ² → **\|τ·ω\|**（机械功率=做功速率）；tc 0.4→**1.5 s**（≥1 个完整周期）；权重 −1.0→**−2.0** | 堵住"加快步频刷低不对称"和"等长收缩算成出力"两个漏洞 |
| 新增 **`base_height_bias`** | 躯干高度靠向参考 **0.765 m**，deadband 0.05 m，权重 −2.0 | **治蹲的主项**。只罚膝角的话策略可把屈曲转移到髋/踝，膝角正常但人照样蹲；躯干高度是绕不过去的最终观测量 |
| 新增 **`knee_bias`** | EMA 膝角工作点靠向参考 **15°**，deadband ±10°，tc 1.5 s，权重 −1.0 | 治蹲的姿态侧。罚**工作点**不是瞬时值，不限制屈伸幅度 |
| `ang_vel_xy_l2` | −0.05 → **−0.2** | 躯干俯仰/横滚角速度，转弯晃 |

参考基准全部来自实测（`scripts/ref_height_stats.py`，0.8–1.3 m/s 档）：

### 实时监控 + 自动早停（`scripts/watch_v2.py`）

用户明确要求"衡量迭代步数与效果的关系，不需要一直训练"。v1 的实测正好
证明必要性：对称性 2400(42.6%) → 2800(46.2%) → 2999(48.7%)，**后期在变差**。

监控盯四个量 + 一个硬门槛，综合分越低越好：

```
score = legAI
      + |cadence − 100| / 100 × 100
      + |knee − 15|    / 15   × 100
      + |height − 0.765| / 0.765 × 100
硬门槛：v_act < 0.7·v_cmd 的评估点整点作废（站着不动当然对称）
早停：iter ≥ 1200 且连续 3 个评估点综合分未改善 >2% → 杀掉训练，报最佳 ckpt
```

四个量互相牵制：只把对称性刷低（比如靠碎步）会被 cadence/knee/height 抓住。

**归因边界（写清楚，别当消融用）**：一次改四项，成功时无法归因到单项。
这是工程修复不是受控消融。

### 3.4.1 更正：「蹲着走」是误诊（2026-10-27 22:10 实测推翻）

给 v1 最终模型（iter 2999）补采躯干高度后，**3.4 的因果链前提被推翻**：

| 量 | 参考实测 | v1 机器人 | 判定 |
|---|---|---|---|
| 躯干高度 | 0.765 m | **0.762 m** | ✅ 没蹲 |
| 膝均屈角 | 15.0° | **16.7°** | ✅ 没蹲 |
| 支撑占比 duty | 人类 0.60 | **0.664** | ✅ 正常 |
| 步频 | 95–103 /min | **136** | ❌ 高 36% |
| 步长 | 1.17–1.27 m | **0.89** | ❌ 短 27% |

**它没有蹲，只是每一步迈得短。** 我加的 `base_height_bias` / `knee_bias`
在 v1 的终点上几乎不产生梯度（都已在 deadband 内）—— 它们治不了碎步。
从零训时仍有价值（约束早期探索方向，别一开始就走向蹲姿），但**不能指望
它们治步态尺度**。

继续往下挖，又连续推翻两个假设，都记录在此避免重犯：

| 假设 | 实测结果 | 结论 |
|---|---|---|
| 髋摆动不足导致步幅小 | 参考 hipROM **13.3°**，机器人 **20.9°** | ❌ 机器人摆得比参考还大 |
| 参考数据打滑（root 速度虚高） | 支撑相脚速中位 0.316 m/s | ❌ 判据用错对象 |

打滑那条走了两次弯路，值得单记：
1. v1 脚本写 `np.diff(fxy[c])` —— 布尔索引把跨段的支撑帧拼成连续序列，
   段间跳变被当成位移，算出 1.15 m/s；
2. 改成段内 diff 后仍有 0.316 m/s，差点判定打滑 —— 但 **key_body 的"脚"是
   踝关节**，支撑期内踝随脚跟→脚尖滚动本来就要前移 0.15–0.2 m，
   0.3 m/s 正是这个正常值。而且这些片段全是转弯 clip，位移主要来自转向。

**已确认**：`key_body_pos` 是**世界坐标**（idx0/1 的 z≈0.05 是脚，
idx2/3 的 z≈0.70，idx4/5 的 z≈1.04 是头/手；root z≈0.75）。

**当前对碎步的最佳解释（待验证）**：v1 的对称惩罚 `EMA(τ², 0.4s)` 本身在
**诱导**高步频（窗口 < 半周期，走得越快越像对称）。v2 把量换成
`EMA(|τ·ω|, 1.5s)` 正是为堵这个后门。

### 3.4.2 v2.1 更正：`ang_vel_xy_l2` 加重是**方向错误**（22:31 重启）

v2 跑到 iter 800 时 `v_act=0.06`（还没学会走），而 v1 在 iter 800 已经 0.97。
查训练日志里各项奖励的实际数值定位拖累来源：

| 奖励项 | 实测值 | 判断 |
|---|---|---|
| `base_height_bias` | **−0.005** | 已在 deadband 内，不是拖累（也印证它治不了碎步） |
| `knee_bias` | **−0.05** | 同上 |
| `leg_work_asymmetry` | −0.16 | 预期内 |
| **`ang_vel_xy_l2`** | **−0.14** | 比 v1 大 4 倍，是上面两项的几十倍 |

`ang_vel_xy_l2` 罚的是**躯干俯仰 + 横滚角速度**。迈大步必然带来更大的躯干
摆动 —— **它在奖励小步幅，与"治碎步"方向正好相反**。转弯不稳的根因更可能是
碎步导致支撑面切换过频，治好步态尺度应当自然改善，不需要靠压躯干角速度治标。

v2.1 的改动：
1. `ang_vel_xy_l2` **回退 -0.2 → -0.05**
2. `feet_air_time` threshold **0.4 → 0.5**（补上真正的步态尺度旋钮。该奖励
   `clamp(reward, max=threshold)`，clamp 是 max 不是 min，短腾空不会变成惩罚；
   且只在 single_stance 给分，不会诱发跳跃）
3. MAX_ITER 3000 → 2400（配合早停，不必训满）

代价：v2 已跑的 836 iter 作废，约 55 分钟。但继续跑下去是在一个方向错误的
配置上浪费 2.5 小时。

### 3.4.3 v2.2 更正：拖累主源是 `leg_work_asymmetry` 权重 -2.0（23:56 重启）

v2.1 回退 ang_vel 后**仍然没学会走路**：

| iter | v_act | 状态 |
|---|---|---|
| 400 | 0.07 | 没在走 |
| 800 | 0.05 | 没在走 |
| 1200 | 0.07 | 没在走（v1 同期 0.97，到 800 已会走） |

由此 `ang_vel_xy_l2` 被排除（回退了也没救回来），排除法只剩一个主嫌疑：
**`leg_work_asymmetry` 权重 -2.0 是 v1 的两倍**。机制上自洽：
- 早期探索期任何迈腿尝试都伴随左右不对称的做功 → -2.0 的惩罚压掉探索；
- 而站着不动时 |τ·ω|≈0 → **该惩罚项为零**，"站着别动"成了局部最优。
v1 用 -1.0（τ² 版）在 iter 800 就学会走路，说明这个量级不挡路。

另发现一个**运维事故**：22:31 重启 v2.1 时旧 v2 训练进程（21:31 启动）没被杀，
两个 4096-env 进程**共抢同一块 GPU 跑了 1 小时 25 分**，且两个进程的输出混写
进同一个日志文件（事后读日志看到 `ang_vel_xy_l2: -0.14`，其实来自已作废的
v2 进程 —— v2.1 自己的 env.yaml 实际是回退后的 -0.05，虚惊一场）。

v2.2 改动（23:56 启动，run 2026-10-27_23-56-50）：
1. `leg_work_asymmetry` weight **-2.0 → -1.0**（回到 v1 实证可学走路的量级；
   tc=1.5s 和 |τ·ω| 两个防 exploit 修复**保留** —— 这才是相对 v1 的真正增量）
2. `feet_air_time` threshold **0.5 → 0.4 回退**（v2.1 的未验证改动，先减变量；
   若碎步复发再单独上这个旋钮）
3. 监控器新增 **never-walked 早停**：到 iter 1000 仍 v_act < 0.7×cmd 直接杀
   （v2.1 的教训：所有评估点因"没在走"作废 → 原早停永不触发 → 白烧 2 小时）
4. 训练日志改用独立文件 `train_fresh_v22.log`（不再和旧进程混写）

归因边界：v2.2 若成功，只能说"降到 v1 量级 + 修 exploit 有效"，无法区分
是权重还是 tc/量换的贡献（未做逐项消融）。若 iter 1000 前后仍未走路，
下一个假设按优先级：① 早期 warmup（前 500 iter 权重 0 再爬升）；
② tc 1.5s 本身拖慢学习。

## 5. 全向视频"20s 站定 / 只转 150°"的诊断（已实测闭环）

`scripts/diag_omni.py` 无渲染重放 omni 脚本并记录 yaw/速度轨迹，结论：

**录制日志证实 8 段脚本全部按时进入，不是崩溃。但真正的问题是能力边界：**

| 动作段 | 指令 | 实际执行 | 判定 |
|---|---|---|---|
| 前进 1.0 m/s | vx=1.0 | vx 0.86–1.05 | ✅ 正常 |
| **行走中左转 90°** | heading+90° | **+74°，达成 82%** | ✅ 基本可用 |
| 侧移 | vy=−0.4 | **vy≈0.00–0.06** | ❌ 完全没执行 |
| 后退 | vx=−0.4 | **vx≈0.00–0.05** | ❌ 完全没执行 |
| **原地右转 −90°** | wz=−0.74 | **实际 −6°，达成 6%** | ❌ 完全不执行 |

"20s 后站定"的真相：18s 起的侧移/后退/原地转三段全部失效，机器人只能站着，
最后一段（30–36s）脚本本身就是停。"只转了约 150°"的观感对应行走转向段的 74°
加上低速段的身体晃动。

**根因（三层叠加）**：
1. 训练指令分布：x∈(−0.5,3.0) 中负值只占 1/7，y∈(−0.5,0.5) 样本少，
   且 heading 模式下 wz 由朝向误差生成而非直接采样 —— 侧移/后退/原地转向
   在训练分布里占比极低；
2. 参考数据集 30 个 clip 全是**前进向**动作（行走/转弯/跑），判别器把策略往
   "向前动"的风格拉；
3. 判别器看不见根线速度（61 维输入里 root_lin_vel 被注释）—— 机器人在侧移
   指令下站着不动，风格奖励**不会因此扣分**，任务奖励单靠占比极低的样本撑不住。

**结论**：当前模型的"全向"诚实的边界是 **任意方向的前进（通过行走中转向实现）**。
画方形路径（4×90° 行走转向，净 360°）可行；侧移/后退/原地转向要可用，
需要重训时提高这些指令的采样概率（训练分布改动，非补丁可治）。
`setup/33_video_ft.sh` 的 omni3 脚本已按此边界重编。
