## 三、开机执行手册（目标：30 分钟内收工）

> 全程远程命令走 `scripts/exec_file.py`（命令文件**首行必须是注释**，防 BOM 吃掉第一条）。

### Step 0｜存活探测（2 min）

写 `tmp/probe.txt`：

```
# probe 2026-11-11
hostname; uptime; date
nvidia-smi --query-gpu=name,memory.used,memory.total --format=csv,noheader
df -h /data 2>/dev/null | tail -1
ls -dt /data/legged_lab/logs/rsl_rr*/*/ 2>/dev/null | head -5
ls -lt /data/logs/*.log 2>/dev/null | head -6
```

执行：

```bash
python scripts/exec_file.py tmp/probe.txt 120 tmp/probe_out.txt
```

**判读**：`nvidia-smi` 报卡 + `df -h /data` 有两个数字 → 活着，往下走；
连不上或 `/data` 不存在 → 直接跳 Step 5 降级预案。

### Step 1｜把 v2.2 的结论挖出来（5 min，**不要开训练**）

```
# v22 status
RUN=/data/legged_lab/logs/rsl_rl/g1_amp/2026-10-27_23-56-50
ls -lt $RUN 2>/dev/null | head -8
echo "=== csv ==="
cat /data/progress/v2_curve.csv 2>/dev/null
echo "=== watch ==="
tail -60 /data/logs/watch_v2.log 2>/dev/null
echo "=== train ==="
tail -30 /data/logs/train_fresh_v2*.log 2>/dev/null
echo "=== gpu ==="
ps -eo pid,etimes,cmd | grep '[t]rain.py'
```

⚠️ 日志名有歧义：`setup/36` 默认 `train_fresh_v2.log`，但文档记录 v2.2 用了
`train_fresh_v22.log`。**用通配 `train_fresh_v2*.log` 一次看全**，别只查一个。

### Step 2｜判定表（看 `v2_curve.csv` 的 `v_act` 列）

| iter 400 的 v_act | 结论 | 动作 |
|---|---|---|
| **≥ 0.70** | 学会走路了 ✅（v1 同期 0.97） | → 走 Step 3A 成功分支 |
| 0.20–0.70 | 走起来了但很慢 | → 先看 iter 800/1200 是否在爬，再定 |
| **< 0.20** | 没学会 ❌（v2/v2.1 都是 0.05–0.07） | → 走 Step 3B 失败分支 |

另查两点：
- `watch_v2.log` 里有没有 `EARLY STOP` → 判断是不是被 never-walked 早停杀的
- `ls $RUN` 里最大 ckpt 编号 → 判断训练实际跑到第几轮

### Step 3A｜成功分支（约 15 min）

```
# eval v22
cd /data/legged_lab && \
/data/envs/isaaclab/bin/python scripts/full_eval.py \
  --ckpt $RUN/model_XXXX.pt --vel 1.0 2>&1 | tail -40
```

然后拉回本地：`python scripts/sync_from_server.py`，
再把 npz 拷进 `backup/eval_out/`，本地跑 `scripts/report_table.py` 出对比表。

**这次不录视频**（录视频要 20 min 且和训练抢 GPU），留给下次。

### Step 3B｜失败分支：立刻上 v2.3（你已经拍板这条）

**顺序很重要：先备份证据，再重训。** 否则日志被新 run 覆盖就没法解释"为什么又失败了"。

1. 存证：`cp /data/logs/train_fresh_v2*.log /data/logs/archive_v22_2026-11-11.log`
2. 判定死法：iter 400 就 <0.2 → 惩罚从第一步就在压制探索；后期才掉 → 另一个原因
3. 设计 v2.3（见下）

#### v2.3 的两种实现，二选一

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A 两阶段**（零代码改动） | 前 300 iter 用 `leg_work_asymmetry` 权重 **0**（等于 v1 配置）训 → 停下 → patch 成 `-1.0` → `08_train_resume.sh` 接着训 | 不改奖励代码，resume 已验证可用；本身就是一组消融 | 硬切换，等于"先学再罚"，可能又踩"改不动固化模式"的老坑 |
| **B 真 warmup**（要改代码） | 在 `mdp/rewards.py` 的函数里读 `env.common_step_counter`，把返回值乘 `min(1, step/WARMUP_STEPS)`，前 ~12000 步（≈500 iter）线性爬升 | 惩罚在 motor primitive 形成期逐渐出现，符合 3.6 的教训 | 要先核实奖励函数能拿到 `env` 的哪些属性，改完必须 `py_compile` + 冒烟 |

**推荐 B**，理由：3.6 那条实测教训（finetune 把 36.7% 打到 37.1%，纹丝不动）说的就是
"约束必须在动作模式形成期施加"。A 是硬切换，本质仍是"先形成再改"。

开工前必须先确认三件事（都是 `grep` 就能答）：
- 奖励函数签名里有没有 `env`
- `env.common_step_counter` 在 legged_lab 里叫什么（Isaac Lab 里通常是这个名字，**要实测确认**）
- 每 iter 采多少步（决定 500 iter 对应多少 step）

**冒烟 3 iter** 看这一项的 scale 是否真在涨，再放全量。

### Step 4｜备份（无论如何都做，5 min）

```bash
python scripts/sync_from_server.py          # 日志/脚本/配置 → backup/server/<时间戳>/
```

ckpt 单独确认（`sync_from_server.py` 默认不拉大文件）：
把 v2.2 最新 ckpt 拷到 `backup/checkpoints/`，命名带上 run 日期。
**这是唯一可能丢的东西，优先级高于一切实验。**

### Step 5｜降级预案：机器没了

判断依据：连不上，或 `ls /data/legged_lab` 报不存在。

| 还有什么 | 能做什么 |
|---|---|
| 本地 `model_4999.pt` | 有主 run 的终版权重，能 resume/finetune、能录新视频 |
| 本地全部视频 + 10-23 前日志 + 22 篇文档 | 报告、面试材料、README 全部不受影响 |
| v2/v2.1/v2.2 三轮失败证据 | **只有 10-28 的文档记录了，服务器日志已丢** → 损失是"证据链"不是结论 |

重建成本：`setup/01~04` 约 90 min（含 Kit 首次冷启动编 shader，换 GPU 后缓存作废要重编）。
重建后直接从 `model_4999.pt` 起 finetune，不必从零训。

1. Step 0 探测 → 活着就继续，死了走 Step 5 并告诉你损失面
