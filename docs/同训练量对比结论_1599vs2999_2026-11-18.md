# 同训练量对比结论：v2.3 model_1599 → model_2999（2026-11-18）

> 这是本项目第一次做到**训练量严格对齐**的横向比较：v2.3 从 1600 续训到 3000
> （`setup/41_resume_v23_to3000.sh`），与 v1 的 2999 同量级。
> 两份数据都是同一套 11 档密集扫描（0.5→3.0，步长 0.25，每档 1500 步，丢前 30%），
> 同口径、同 seed、同脚本 → **前后可直接比较**（这一点此前一直做不到）。
>
> 数据：`gait_v23_1599_sweep11.npz` / `gait_v23_resumed_sweep11.npz`
> 脚本：`scripts/compare_sweeps.py`（含两个预注册问题的自动裁决）

## 一句话结论

**续训解决了"跑不到目标速度"，但没有解决"走得对称"，而且用户最关心的常速档反而更跛了。**
速度跟踪接近翻倍地改善；对称性出现「全档均值改善、@1.0 常速恶化」的分裂——
**这个平均值是陷阱，不能用**（又一次踩到 MEMORY 3.7 的"合成指标被反向抵消"，这次是跨速度抵消）。

## 一、速度跟踪：大幅改善（硬结论）

| 指标 | 1599 | 2999 | 变化 |
|---|---|---|---|
| Pearson ρ(cmd, v_act) | 0.9922 | **0.9983** | ↑ |
| MAE | 0.158 | **0.082 m/s** | 几乎减半 |
| 低速段(≤1.5) 平均\|err\| | 0.017 | 0.030 | 基本不变（略差） |
| **高速段(≥2.0) 平均\|err\|** | **0.288** | **0.124 m/s** | **↓57%，明显缓解** |
| 3.0 m/s 档 v_act | 2.472 | **2.899** | err −0.527 → −0.097 |
| 最大欠速 | −0.528 | −0.179 | 收敛 |

**这直接修正了上一份文档的推断。** 见下方更正块。

## 二、出力不对称 legAI：平均值是陷阱（重点，必须小心）

| v_cmd | legAI 1599 | legAI 2999 | 变化 |
|---|---|---|---|
| 0.50 | 47.3 | 50.6 | +3.3 ❌ |
| 0.75 | 40.0 | 54.1 | +14.1 ❌ |
| **1.00** | **34.8** | **51.8** | **+17.0 ❌❌** |
| 1.25 | 42.5 | 43.1 | +0.6 |
| 1.50 | 46.4 | 41.0 | −5.4 |
| 1.75 | 51.0 | 31.1 | −20.0 ✅ |
| 2.00 | 54.2 | 32.3 | −21.9 ✅ |
| 2.25 | 58.9 | 39.5 | −19.4 ✅ |
| 2.50 | 62.7 | 47.7 | −15.0 ✅ |
| 2.75 | 66.5 | 51.4 | −15.2 ✅ |
| 3.00 | 67.8 | 53.7 | −14.2 ✅ |
| **全档均值** | **52.6** | **45.5** | **−7.1（看着像改善）** |

- **高速段（≥1.75）确实改善了 14–22 个百分点**，把全档均值拉低到 −7.1%。
- **但常速档 0.5/0.75/1.0 全部恶化**，尤其 **@1.0 m/s 从 34.8% 涨到 51.8%（+17）**。
- 而 @1.0 m/s 正是用户当初看 `f2800_walk10` 提"轻微跛行还没根治"的那个速度。
  **所以对用户主诉而言，续训后是变差了，不是变好。**
- 若只报"全档均值 52.6→45.5 改善"，就是用高速段的改善掩盖常速段的恶化 ——
  MEMORY 3.7「逐关节先合成再比会被反向抵消」的**跨速度版本**。
  **对称性类结论一律要看逐档，绝不先平均再比。**

> ⚠️ 口径 caveat：v1-2999 的 legAI=48.7% 是 11-16 用单档 eval 测的，与这里
> 「11 档并行扫描里的一路 1.0」不完全同采样条件。因此**不能**据此断言
> "v2.3 比 v1 差"。但 1599→2999 这份前后对比是严格同口径的，"+17 恶化"是硬的。

## 三、步态尺度：部分改善，碎步仍在

| @1.0 m/s | 1599 | 2999 | 参考 |
|---|---|---|---|
| cadence | 137.1 | 128.6 | 95–103 |
| stride | 0.852 | 0.891 | 1.17–1.27 |
| knee° | 21.4 | **16.7** | 13–15 |
| duty | 0.587 | 0.611 | ~0.60 |

膝角明显回落（21.4→16.7，接近参考上沿）、duty 回到人类水平、步频略降、步长略增
—— 都是**向参考靠近**的小幅改善。但 cadence 仍高 25–35%、stride 仍短 ~25%，
**碎步/短步没有被根治**，与 11-16 的判断一致：`feet_air_time` / `knee_bias`（死区）
对步态尺度没有实际作用力。

## 四、更正块：撤回上一份文档的一个推断（保留原文）

> **原推断（见 `docs/速度扫描结论_2026-11-18.md` §4，写于 15:50，保留不删）**：
> "高速掉速最可能不是训练 bug，而是**参考动作数据分布缺陷**：LAFAN1 30 段实测中
> 2.0 m/s 附近仅约 5% 帧…判别器把高速 gait 判成不像人 → 策略宁可欠速。"
> 当时标注为"推断，未做受控消融"。

**更正（16:45，同训练量实验后）**：这个推断**被本轮实验削弱，不作数**。
如果只是数据分布/判别器压制，那么**增加训练量不该缓解掉速**；但实测续训到 3000 后
高速段 |err| 从 0.288 降到 0.124（−57%）、3.0 档从 2.472 追到 2.899。
→ **高速掉速的主因是训练量不足（1600 iter 没收敛），不是数据分布缺陷。**
LAFAN1 高速样本稀疏可能仍有次要影响（残余欠速 −0.10~−0.18 未消失），
但**不能再把它当主因写进任何材料**。

这条更正本身是个好素材：它演示了"先提出机制假设 → 设计一个能证伪它的实验
（对齐训练量）→ 假设被数据削弱 → 主动撤回"，而不是找补。

## 五、诚实边界与结论强度

| 结论 | 强度 | 依据 |
|---|---|---|
| 续训后高速掉速明显缓解 | **硬** | 同口径前后对比，训练量对齐 |
| 高速掉速主因是训练量不足，非数据分布 | **较硬（推翻了原推断）** | 反证法：加训练量即缓解 |
| @1.0 m/s legAI 恶化 +17 | **硬** | 严格同口径前后对比 |
| 全档均值 −7.1% 是"改善" | **无效结论** | 被跨速度反向抵消污染 |
| 碎步/短步未根治 | **硬** | cadence/stride 仍在参考外 |
| warmup 是否根治了不对称 | **否，且比早期更差（常速）** | 1600 时最好 34.8，3000 时 51.8 |
| 与 v1 的跨方法横比 | **不成立** | 采样口径不同，见 §2 caveat |

## 六、这轮之后，项目真实状态该怎么对外说

- **能讲**：AMP+速度指令在 0.5–3.0 m/s 全程单调响应（ρ=0.998）、低速精确、
  高速小额度欠速（≤0.18 m/s）；warmup 让"能否学会走路"从学不会变成能学会、
  但相变推迟一个窗口；一整套同口径评测与"预注册阈值 + 自动裁决"的方法论。
- **必须承认未解决**：左右出力不对称（常速 ~52%，人类 <5%）、碎步短步、
  侧移/后退/原地转向不可用；且对称性**训练后期回升**（与 v1 同病）。
- **下一轮着力点**（不是调权重）：
  1. 对称约束要在**整个训练期**持续有效，而不是只在形成期 warmup。
     现观察到"1600 最好、3000 回升"，说明后期任务奖励又压过了对称项 →
     考虑把对称项做成随速度/训练进度自适应，或加一个防回升的正则。
  2. 步态尺度要换**能直接拉动步长的显式奖励**（stride_length / foot_clearance），
     `feet_air_time` 与死区里的 `knee_bias` 已证实无效。
  3. 补录 `model_2999` 视频做肉眼验收 —— **本轮未出片，见 §八**。已有
     `v23_1599_walk10.mp4`（1600 iter 版）可看跛行观感。

## 八、视频录制：2999 未出片，及一次归因更正

**结果**：`v23_1599_walk10.mp4`（1600 iter 版）15:26 成功录出，2.6 MB，已备份并
拷到仓库根目录，可直接看跛行观感。`v23_2999_walk10.mp4` **两次尝试都卡死**，
日志停在 `terrain_importer` 之后不再前进，未出片。

**更正（保留 11-16 原文）**：`docs/v2.2结案与v2.3方案.md` 和 `memory/2026-11-16.md`
当时把"卡 32 分钟"归因为"单环境 headless 渲染慢 / replicator 阻塞"，并猜测
"漏打补丁 / 没用 Play task"。**本轮实测两条都不成立**：

| 排查 | 结论 |
|---|---|
| 漏补丁 / 没用 Play task | ❌ 不是。今天 1599 用**同一个 40 脚本**（含两个补丁 + `G1-Play-v0`）2分40秒出片 |
| 缺 `videos/play/` 目录 | ❌ 不是。续训的新 run 确实缺该目录，手动 `mkdir -p` 后重录**仍卡在同一行** |
| **真因** | ✅ **headless `--video` 在同一会话第 2 次及以后启动，会卡在 Kit 渲染子系统初始化** |

证据是成功/失败两份日志的对比：成功那次 `terrain_importer` 之后有一串渲染初始化行
（加载天空 HDR `kloofendal_...hdr`、`FabricManager::initializePointInstancer`、
`OgnSdPostRenderVarToHost`）；**失败那次这些行一行都没有**，即卡在进入渲染器之前。
今天 15:23 是开机后第一个 Kit 进程 → 成功；16:45 / 16:50 是第 2、3 个 → 都卡。
11-16 那次也是当天多轮 eval/训练之后的录制，同一现象。

**可复用规律**：
1. 单会话内**只录第一段视频**（第一个 Kit 进程），要录多段就分批重启会话。
2. 录完立刻另存（本来就有的规矩）。
3. `pkill -9 -f "xxx.sh"` 会**自杀**——远程命令文件内容会进入承载 shell 的命令行，
   `-f` 匹配到它自己。清理进程一律**按精确 PID `kill -9`**。

**不影响本轮结论**：所有量化结论来自 npz，不依赖视频；2999 视频只是肉眼验收的补充。
